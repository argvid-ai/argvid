# Requests for comments

## Responsibility

Hold public proposals that may change interfaces, architecture, compatibility, or contributor workflow.

## Non-goals

Business strategy, informal meeting notes, accepted decisions without rationale, or implementation-only details.

## Inputs and outputs

Inputs are a problem statement and evidence; outputs are reviewed proposals with status and alternatives.

## Dependencies

Depends on current context, contracts, and prior decisions.

## Invariants

Every RFC states status, owner, scope, alternatives, compatibility impact, and verification plan.

## Start condition

Create an RFC when a change crosses module boundaries or alters a public contract.

## Ownership and review

Proposal owner plus affected module and safety reviewers.

## Verification

Accepted RFCs link to implementation evidence and a durable decision record when appropriate.

## Public use cases

Propose shared contract or architecture changes before activating implementations; include public synthetic acceptance evidence.

## License and data

Source and documentation default to Apache-2.0. Use synthetic or explicitly licensed public inputs with recorded provenance; publication rights require human review. Third-party assets, weights, datasets, and hardware design sources need separate license review. This documented boundary is not an activated implementation, released compatibility guarantee, or completed HIL result.
